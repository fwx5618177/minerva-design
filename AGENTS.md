Documentation demos can depend on docs context; standalone recipes must include their own entry, styles, providers and dependencies.

## Boundaries and compatibility

Only [minerva-design](packages/minerva-design/package.json) is published. `@minerva/*` packages are private implementation workspaces; user docs, recipes, demos and README examples import public `minerva-design` entries. Keep core platform-neutral: no DOM access. Framework event names, slots, controlled / model-owned state, portals and native host events can differ: consult actual renderer APIs and manifest limitations before propagating a change. Shared tests use happy-dom / native test hosts. The Chrome UI lane checks specific responsive layouts, theme/control contrast and documentation interactions after a production build; neither lane certifies GPU output or native devices. React Native has no AutoComplete keyboard-highlight suite; Taro / uni / Weapp coverage is described in the shared-suite guide.

Treat exported props, events, CSS tokens, public parts / states and entry points as compatibility surfaces. Preserve existing consumers or document a deliberate breaking migration. Public package API, style and runtime changes in any renderer need a `minerva-design` changeset via `pnpm changeset`; do not manually bump versions. See [release policy](docs/releasing.md).

## Media playback

The shared web implementation lives in [packages/media-player](packages/media-player). The React [MediaPlayer adapter](packages/react/src/components/MediaPlayer) owns only Minerva presentation/API compatibility; playback state and engines have one implementation. Advanced consumers import `minerva-design/media-player` and its CSS subpath. Framework/native hosts keep their declared limitations.

Run `pnpm test:media-player` after the aggregate build for unit tests and real installed-tarball browser playback. Use an installed Chrome/Chromium or set `CHROME_PATH`; browser tests use Node WebSocket and Chrome DevTools Protocol without browser automation dependencies. Desktop, Android and iPhone viewport checks run in Chrome; Firefox, WebKit and physical devices are explicitly unverified. CI runs `pnpm test:media-player:product` separately from source coverage so real browsers do not compete with hundreds of source-test workers. Headless Linux needs a working audio output: CI starts PulseAudio with a null sink; codec errors must still fail the tests. It checks browser/device emulation, not physical native devices.

## Before merging

Focused checks above shorten iteration; they do not replace the [CI verify job](.github/workflows/ci.yml). Run `pnpm lint`, `pnpm build`, inspect generated drift (`git diff --exit-code` after generated changes are committed), `pnpm typecheck`, `pnpm format:check`, `pnpm test:release`, `pnpm test:tools`, `pnpm test:migration`, `pnpm test:coverage`, `pnpm --filter @minerva/docs check:mini-api`, `pnpm --filter @minerva/docs check:reference`, `pnpm test:browser:ui`, `pnpm test:dist`, `pnpm check:package`. Use `pnpm test` for the complete source suite without coverage. Report any unavailable environment or failing check accurately.

[Navigation consistency checks](tests/contracts/agent-guide.test.ts) resolve linked paths, public entries, workspace scripts / script targets and Vitest project names, and compare the listed full checks with CI. Run `pnpm exec vitest run --project contracts agent-guide` when moving these interfaces.

The browser UI lane runs with an installed Chrome/Chromium (or `CHROME_PATH`) and manages its own preview and temporary profile. `pnpm test:browser:ui` writes diagnostic measurements to `.artifacts/ui-issues/`; it is part of CI verify.
